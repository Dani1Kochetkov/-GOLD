# Архитектура GOLD DAYZ

Документ объясняет, как устроен сервер, почему логика вынесена из RAGE и как проходит путь одного выстрела и одного снапшота.

---

## 1. Слои

```
┌─────────────────────────────────────────────────────────────┐
│ CEF UI (client_packages/gold/ui)                            │
│  HUD · инвентарь · карта · смерть · тосты                    │
└───────────────▲──────────────────────────┬──────────────────┘
                │ window.goldUI.receive    │ mp.trigger('goldui:action')
                │ (JSON)                   │ (JSON)
┌───────────────┴──────────────────────────▼──────────────────┐

│  index (события/клавиши) · zombies (педы, интерполяция)      │

┌───────────────┴──────────────────────────▼──────────────────┐

│  playerJoin/Ready/Quit/Death · player.call · health/weapons  │
│  setInterval(50ms) → чтение позиций → game.tick()            │
└───────────────▲──────────────────────────┬──────────────────┘
                │ net.send/broadcast/chat  │ вызовы методов
┌───────────────┴──────────────────────────▼──────────────────┐
│ server/game.js — игровое ядро                                │
│  игроки · выживание · инвентарь · зомби · лут · PvP · метрики │
└───────────────▲─────────────────────────────────────────────┘

┌───────────────┴─────────────────────────────────────────────┐

```

Правило: **`shared/` не знает про RAGE**, `game.js` не знает про глобальный `mp`, `server/index.js` знает всё про RAGE и ничего про правила игры.

Благодаря этому `tools/sim.js` подставляет фейковый `net` и гоняет настоящий мир: ИИ, лут, стрельбу, смерть, лут-респавн — без GTA.

## 2. Тик

`setInterval(..., 50)` в `server/index.js`:

1. `syncPositions()` — читает `player.position/heading/dimension` через RAGE и отдаёт в `game.setPlayerState`.
2. `game.tick(now)` — внутри сам держит шаг `server.tickMs = 100`:
   * обновляет игровое время суток (`world.dayLengthMs`, по умолчанию 40 минут = сутки);
   * `tickPlayerSurvival` — голод/жажда/кровь/радиация/температура/стамина, токсичные зоны, безопасные зоны, авт-респавн;
   * `tickZombies` — ИИ и атаки;
   * `tickZombieSpawning` — добор популяции;
   * `tickLoot` — пополнение зон рядом с игроками и удаление просроченного;
   * `tickNoise` — очистка событий шума;
   * `tickPlayerNetwork` — HUD (2 Гц) и снапшоты зомби с адаптивным интервалом;
   * сохранение профилей раз в минуту;
   * метрики времени тика.
3. `syncHealth`, `syncWeapons`, `syncLives` — зеркалирование состояния в движок: здоровье, выданное оружие, `spawn` после респавна.

Тик никогда не бросает исключения наружу: в `index.js` всё обёрнуто в `try/catch`, ошибка пишется в лог и не убивает сервер.

### Время

Сервер считает `worldHour = start + elapsed / dayLengthMs * 24`. Клиент ставит часы по HUD-пакету и держит `pauseClock(true)`, поэтому ночь синхронна у всех и не «уплывает» от локального времени клиента.

## 3. Протокол снапшотов

### Почему массив, а не объекты

`player.call` ограничен 8192 байтами, и это **единственный** транспорт для состояния зомби. Поэтому:

```json
{"t":1700000000123,"z":[[12,-275.12,6450.44,32,271.5,3,100,0], ...]}
```

* `id` — серверный номер;
* `x,y,z` — позиция с округлением до 2 знаков;
* `heading` — 0.1°;
* `state` — 0 idle, 1 wander, 2 investigate, 3 chase, 4 attack;
* `hp` — процент (0–100);
* `typeCode` — индекс в `data/zombies.json`.

Пустые ключи и массивы вместо объектов экономят ~40% размера. Бюджет проверяется на каждом шаге:

```js
buildSnapshot(zombies, { position, radius, maxBytes, maxEntities, dimension })
```

Функция фильтрует мёртвых/чужие измерения/дальних, сортирует по расстоянию и **обрезает по байтам**, а не только по количеству. Всё, что не влезло, помечается `dropped` (никогда не теряется молча).

### Адаптивность

| Условие | Интервал |
|---|---|
| рядом нет зомби | 200 мс (только чтобы сообщить «пусто») |
| < 15 игроков онлайн | 50 мс |
| ≥ 15 игроков | 100 мс |

`chooseInterval(playersOnline, zombiesVisible)` — чистая функция, покрыта тестами.

### Клиентская интерполяция

`shared/sync.js`:

* каждый снапшот заводит/обновляет `entity.from → entity.to`, `startedAt`, `duration` (по фактической дельте прихода, 40–500 мс);
* каждый кадр `computePosition/computeHeading` линейно интерполируют;
* угол идёт по кратчайшей дуге (через 0°, а не через 180°);
* нет экстраполяции за пределы цели (t ≤ 1), чтобы педы не «проскакивали» сквозь стены;
* если сущность не приходила 3 секунды — удаляется и пед уничтожается.

### Клиентский пед

* модель грузится через `requestModel`/`hasModelLoaded`, создание откладывается до загрузки;
* `invincible`, `setProofs`, `setCanRagdoll(false)`, `setCanBeTargetted(false)`, блокировка нетемпоральных событий — чтобы движок не убил зомби раньше сервера;
* движение: `taskGoStraightToCoord` переустанавливается раз в 600 мс для анимации шага, а `setCoords` используется как страховка при расхождении > 4.5 м;
* смерть: рагдолл + удаление через 1.5 с (сервер уже убрал его из снапшотов).

## 4. ИИ зомби (shared/zombie-ai.js)

Состояния: `idle → wander → investigate → chase → attack`, плюс `dead`.

Каждое «размышление» (~400 мс × джиттер):

1. Если есть цель — проверяем, жива ли, в том же ли измерении, не в безопасной зоне, не убежала ли дальше `chaseRange`.
2. Иначе ищем ближайшего игрока в `detectRange` (для уже преследующего — `chaseRange`).
3. Если цели нет, но был шум (`hearNoise`, выстрел/крик) — идём к точке шума `NOISE_FORGET_MS = 6 с`.
4. Если цели нет вообще — патрулируем зону: случайная точка в 55% радиуса, иногда стоим.
5. Любая точка назначения ограничивается `radius + 60` — зомби не уходят через полкарты.
6. В `attack`: если игрок в `attackRange` и кулдаун прошёл — событие `attack` с уроном; сервер повторно проверяет дистанцию перед нанесением.

Детерминизм: один `Rng` (mulberry32) на мир, seed из конфига/ENV. Это позволяет воспроизводить баги: одинаковый seed + одинаковые вводы = одинаковая картина.

Шум: выстрел регистрирует `{pos, radius, at, dimension}`; сервер прогоняет всех зомби и вызывает `hearNoise`. Крикун дополнительно «кричит», поднимая соседей (событие `scream`).

## 5. Инвентарь (shared/inventory.js)

```
container = {
  id, base: 18,
  slots: [ {itemId, count, meta} | null, ... ],
  equipment: { primary, melee, back, armor, mask, hands }
}
```

* `base` — слоты без экипировки; рюкзак/разгрузка добавляют `storage` сверху (пересчёт `slotCount`).
* Стаки: до `stack`, только для предметов без `meta` (патроны в магазине не стакаются).
* Вес: сумма `weight × count` по слотам + экипировка. `addItem` принимает `maxWeight` и возвращает `{added, leftover, reason}` — частичный подбор.
* `equip/unequip` переносят предмет между слотом и экипировкой, проверяют конфликты и не позволяют снять рюкзак, если верхние слоты заняты (`storage-busy`).
* `loadWeapon/consumeAmmo` — магазин и патроны.
* `sanitizeInventory` — валидация профиля/сети: неизвестные id, переполненные стаки и чужая экипировка отбрасываются.

Сервер — единственный авторитет. Клиентский UI только отправляет намерения (`move/equip/use/drop/reload`), сервер отвечает свежим снапшотом инвентаря.

## 6. Выживание (shared/survival.js)

```
health 100 · blood 100 · hunger 100 · thirst 100 · stamina 100
temperature 37 · radiation 0 · bleeding 0..3
```

* голод −0.05/с, жажда −0.07/с (≈30 и ≈24 минуты с полной шкалы);
* на нуле еда/вода отнимают здоровье (−0.5 и −0.7 HP/с);
* кровотечение: −1.4 × уровень HP/с и −3 × уровень крови/с;
* радиация: медленный урон, накапливается в токсичных зонах;
* холод (< 35.2 °C) — урон, мокрый игрок мёрзнет быстрее;
* стамина: спринт тратит, перегруз (> 100% веса) режет восстановление до 35%;
* смерть фиксирует причину (`bloodloss`, `hypothermia`, `dehydration`, …) и попадает в экран смерти.

`tick` ограничивает `dt` пятью секундами — лаг-спайк не должен «убить» игрока за один вызов.

## 7. Поток выстрела

1. Клиент: `LMB` → проверка панели/смерти → `Combat.attack()`.
2. Проверка темпа и патронов (локальная копия для отзывчивости).
3. Луч из камеры: `getGameplayCamCoord/getGameplayCamRot`, `mp.raycasting.testPointToPoint` (map+objects+peds) — получаем точку попадания.
4. `mp.events.callRemote('gold:shot', JSON.stringify({o:[...], t:[...]}))`.
5. Сервер (`handleShot`):
   * rate-limit 20/с;
   * берёт **экипированное** оружие (клиентское `w` не используется);
   * проверяет магазин, списывает патрон;
   * регистрирует шум (`noise` из `data/items.json`);
   * `resolveAttack`: ищет ближайшую цель, у которой расстояние до луча < 0.8–0.9 м и дистанция от игрока ≤ `range + допуск`;
   * урон = `damage × (headshot ? 2 : 1)`, бронник режет на 15%;
   * убийство зомби → очки, лут-ролл, broadcast `zombieKilled`;
   * убийство игрока → дроп инвентаря, килл-фид, счёт.
6. Клиент получает `gold:hit` (hit-маркер), `gold:shot` (остаток патронов), `gold:damage` (виньетка).

Движок тоже стреляет нативно (звук, анимация, вспышка), но урон считает только сервер. Педы зомби неуязвимы для движка.

## 8. Пакеты и лимиты

| Событие | Кто → кому | Размер | Частота |
|---|---|---|---|
| `gold:catalog` | сервер → клиент | ≤ 7800 Б, нарезается | 1 раз при входе |
| `gold:map` | сервер → клиент | ~3–5 КБ | 1 раз / `/reload` |
| `gold:inventory` | сервер → клиент | ~0.3–2 КБ | по изменениям |
| `gold:hud` | сервер → клиент | ~250 Б | 2 Гц |
| `gold:zombies` | сервер → клиент | ~0.7–4.7 КБ | 5–20 Гц |
| `gold:shot` | клиент → сервер | ~120 Б | ≤ 20/с |
| `gold:moveState` | клиент → сервер | ~40 Б | 4 Гц |

Все входящие строки проходят `safeJsonParse` с лимитом байт, все действия — через `RateLimiter` (`shared/netcode.js`).

## 9. Надёжность

* Любой обработчик события обёрнут в `try/catch` (`onClient`, команды, `guard`), ошибка идёт в `logs/gold-dayz.log`.
* Профили пишутся атомарно (`.tmp` + `rename`).
* Снапшоты и каталог режутся по байтам, а не по «примерно».
* `npm run check` проверяет данные, синтаксис, бандл, бюджеты и дубликаты команд — до запуска.
* `npm run sim` ловит регрессии в логике без GTA.
* CI прогоняет всё это на каждый push.
